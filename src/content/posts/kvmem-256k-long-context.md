# 16G 显存塞进 25 万 token 上下文：KVMem 分层 KV 实测，附一次图像问答

上一篇写完了「单卡跑 27B」，收尾时留了句刺：上下文开到 64K 就到顶了，模型自己训练时见过 262,144，是硬件拖后腿。

那时候我的解法是**压缩**——把长资料先摘要再喂进去。好用，但有损：同一份 17 个文件的语料，压缩跑完 45 分钟，17 行结论里只有 9 行还保得住原始精度。摘要能把窗口"变小"，可我想干的是**把窗口变大**。

于是这周折腾了 [kvmem-llama.cpp](https://github.com/kvmem/kvmem-llama.cpp)：它把 KV cache 分层——GPU 只常驻一小撮（我给的预算 32K token），其余的 KV 块扔到主机内存里存着，每轮请求按 query 检索回来。原理听着比压缩更"作弊"，但它确实是**无损**的：喂进去的是原文。

结论先摆这儿：**在一张 16 GB 的 Tesla T10 上，单发 257,402 token、三根针全部准确捞出；24.7 万 token 的上下文里再塞一张图，文本针和视觉针也双双读对。**

代价也很清楚，后面一笔一笔算。

## 一、编译：官方配方是给新卡写的

我挑的是仓库指定的 **v0.16.0-rc1**，llama.cpp 子模块按 pin 的 commit 拉下来，再跑 `scripts/apply-patches.sh` 把 KVMem 那层补丁打上去（回显 `applied current KVMem patch to pinned llama.cpp` 才算数）。

三个小坑，都在意料之外、情理之中：

- **CUDA 架构要自己填**。CMake 默认给的 `120a` 是给 RTX 5060 Ti 那代卡的（compute capability 12.0），我这台 T10 是 **7.5**，不写对等于白编。传 `CMAKE_CUDA_ARCHITECTURES=75` 了事。
- **CUDA 不在标准路径**。这台机器的 CUDA 装在 `/opt/cuda`，CMake 只翻 `/usr/local/cuda`，于是报 `Could NOT find CUDAToolkit`。加 `CUDAToolkit_ROOT=/opt/cuda` 就过了。
- **没有 unzip**。拿 `python3 -m zipfile` 解包，别跟 shell 较劲。

顺手记一笔：官方 README 的验证基线是 RTX 5060 Ti（sm_120）加 CUDA 13.2.86；我这台是老架构 sm_75 加 CUDA 13.4.59，属于**官方没验证过的组合**。它编出来能跑、后面探针也全过，算是我自己补的一格。

## 二、启动：官方脚本硬编码了 MTP

第一次点火直接死：

```
failed to create MTP context
```

原因在官方启动脚本里——`scripts/start-server.py` 写死了 `--spec-type draft-mtp`，要求模型带 MTP（多 token 预测）层。我手上这份权重是 **非 MTP** 的 3.0 版（当初选它就是图稳定），于是这条参数直接把服务按死在启动阶段。

绕法很朴素：**别用官方脚本，直接调二进制，把那条参数删掉**：

```bash
llama-kvmem-server \
  -m <模型.gguf> --mmproj <mmproj.gguf> \
  --no-mmproj-offload --image-max-tokens 512 \
  -c 262144 -n 12288 \
  --kvmem-budget 32768 --kvmem-gen-reserve 12288 \
  --kv-dtype q5_0 --enable-thinking --reasoning-budget 4096
```

少了 MTP 只是没有投机加速，**分层 KV 那套（GPU 常驻 32K + 主机内存块池 + 查询检索）照常工作**。服务自报的样子：

```
kvmem=1  method=retrieval  n_ctx=262144  spec=off  n_max=3  think=1  rbudget=4096
```

## 三、探针：怎么证明"它真的记住了 25 万 token 前的那句话"

长上下文的测试最容易自欺。我用的语料是 17 个源码文件（每个约 72 KB，合计 1.2 MB ≈ 41 万 token），每个文件里埋一行 `MODULE_KEY_Mxx = "KEY-xxxxxxxx"` 和一行 `MAX_RETRIES`。

探针脚本干三件事：

1. 按**字符预算**喂文件，喂到多少就报告多少，并打印**真正进了上下文的文件列表**；
2. **只从真正喂进去的文件里取针**（真值在脚本内部算好）；
3. 只输出 `PASS` / `FAIL`，不打印模型的推理过程。

第 2 条是血泪。第一版脚本按固定的文件编号提问，结果 char 预算只喂进了前 9 个文件，问第 11、17 个文件——**文档压根没进去，却被记成了"检索失败"**。从那以后我信一句话：判 FAIL 之前，先证明"针真的在上下文里"。

另外，字符 → token 的比例要**先量再用**：拿两万字符发一次小请求，读 `usage.prompt_tokens` 反推。这份源码语料是 **2.91 字符/token**，所以 20 万 token 对应约 58 万字符。估偏一个量级，就是白烧一次十几分钟的长 prefill。

## 四、前三轮全部失败——三种不同的失败

现在回头看，这三轮的失败比成功有价值：

| 轮次 | 现象 | 真因 |
|---|---|---|
| r1 | 直接 `HTTP 400` | 语料 275k token > 逻辑窗口 262,144，超窗口 |
| r1' | 跑了 585 秒，**一行答案都没有**（`finish: length`） | 思考模式把 `max_tokens=600` 全烧在思考上 |
| r2 | 3000 token 预算，还是空输出（日志里 reasoning 8881 字符） | 思考预算 4096 > 请求上限 3000，仍旧答不完 |
| r3 | Q1 过，Q2/Q3 失败 | **探针设计缺陷**：问的文件没进上下文 |

第三轮那个坑前面说过了。前两轮教的是一条很实用的规律：**开了思考模式的服务，请求里的 `max_tokens` 必须大于 `--reasoning-budget`**，否则它会安安静静地把额度全用来"想"，然后吐出零个字符，而 `finish_reason` 是 `length`——看起来像模型没答出来，其实是预算被吃光了。修法不用重启服务，请求里加 `"chat_template_kwargs": {"enable_thinking": false}` 就行。

顺带一个好玩的观察：r2 的耗时是 r1' 的 38%（224 秒 vs 585 秒），**因为 prompt 一模一样，KV 缓存命中了**。

## 五、第一次真的赢：222,367 token，三针全中

探针修对之后，第一发就是好消息：

```
fed files    : 9 (module_01.py ... module_09.py)
prompt_tokens: 222367   completion: 32   finish: stop
elapsed      : 631.6 s
Q1 (key in module_03.py)     : PASS
Q2 (retries in module_05.py) : PASS
Q3 (key in module_09.py)     : PASS   <- 最深的那个文件
```

22 万 token 全过，跑了 10 分半，而且**换了个 slot 又来了一遍，还是 3/3**。这一发就把"200k 目标"钉住了。

## 六、往上顶：257,402 token 也过，但 24.7 万那档会漏

窗口是 262,144，那就直接顶到天花板。探针改成"末位文件允许截断，只要针还在前 35%"，一次把 11 个文件灌进去：

```
fed files    : 11 (module_01.py ... module_11.py)  [last file TRUNCATED to 30222 chars]
context chars: 750273 (~257825 tokens @2.91)
prompt_tokens: 257402   completion: 32   finish: stop
elapsed      : 733.9 s
Q1 / Q2 / Q3 :  PASS / PASS / PASS
```

12 分 14 秒，**257,402 token，三针全中**，而且里面就有上一轮漏掉的那块。这个数字我后来又独立复跑了一趟（758.1 秒），还是 3/3——**两轮都顶到窗口边缘，都全中**。

但中间那一档很有意思：**24.7 万 token（10 个文件）那组，稳定 2/3**——漏的是靠前的 `module_03`，模型答成了邻近 `module_05` 的值。同一份输入我跑了两次，703 秒和 706 秒，**两次都在同一个地方漏**。

于是三条结论，都是我原来没想到的：

- **召回不是"越大越差"的单调曲线**。24.7 万漏、25.7 万反而全中——多喂一块文件，能让老块被重新捞回来。检索质量跟**输入的块结构**有关，不只是长度。
- **内存压力会静默劣化检索**。有一轮（8 个文件、19.7 万 token）也是 2/3，那次的干扰变量是主机内存被块池吃满；重启服务清空块池后，同样的输入就正常了。**所以长跑必须给块池设上限**（`--kvmem-cpu-gb`），不然它会不声不响地开始答错。
- **判 FAIL 前要比一遍针的唯一性**。各个文件的针值要先 md5 去重——不然"答成了邻近文件的值"很容易被误读成"检索失败"，其实是针撞了。

![针尖召回实测：22 万稳定 3/3，24.7 万稳定漏靠前的块，25.7 万又全中](/images/posts/kvmem-256k-long-context/02.webp)

## 七、多模态：24.7 万 token 里夹一张图，也读得对

既然上下文这么长，那"长资料 + 一张图"能不能一起喂？这一发我让探针先生成一张图：白底黑框，中间一行随机验证码 `VZ-XXXX-XXXX`（每次跑都重新抽），然后把它和 10 个文件（24.7 万 token）一起塞进去，问两件事——**文本针（module_03 的 KEY）和图里的验证码**：

```
prompt_tokens: 247543   completion: 27   finish: stop
elapsed      : 718.7 s
A1 (text needle, module_03.py) : PASS
A2 (visual needle)             : PASS
```

双 PASS。24.7 万 token 的文本里，上一节那组还在漏 `module_03`，这次却捞回来了——**多模态那一发里多了一块"图"，块结构变了**，又一次印证了上面那条。视觉编码走官方配方放在 CPU 上跑（`--no-mmproj-offload`），所以整趟慢一点，11 分 59 秒。

顺便说，这个"图里藏随机码"的针法我很喜欢：码是运行时抽的，**模型不可能背过**，读对就是真的看见了。

![多模态探针：一张带随机验证码的图 + 24.7 万 token 文本，两个问题都答对](/images/posts/kvmem-256k-long-context/05.webp)

## 八、对照组：不用 KVMem，同一张卡能到哪

没有对照的数字不算数字。同机、同模型、同一套语料，换回常规 `llama-server`：

| | 常规 llama-server | KVMem |
|---|---|---|
| 逻辑窗口 / 槽位 | 90,112（单槽）／**45,056**（开 2 槽） | **262,144**（单槽） |
| 实测最大单发 | **85,842 token**，再多直接 400 | **257,402 token** |
| 超限表现 | `request (89986 tokens) exceeds the available context size (45056 tokens)` | —— |
| 85,842 token 那发的 3 根针 | 3/3 | 3/3 |

那句 400 的原文值得贴出来：常规服务开两槽提吞吐，**窗口是按槽位均分的**，一开 2 槽单请求就只剩 45,056——**并发和窗口在常规服务里是同一笔预算**。KVMem 反过来，它干脆没有并发：严格单 slot，第二个请求只能排队。

速度上，两边的账是这样：

![速度对比：常规服务的预填充 361.9 tok/s，KVMem 在 22 万 token 上端到端 352 tok/s](/images/posts/kvmem-256k-long-context/03.webp)

- 常规服务 85,842 token 那发：prefill **237.2 秒（361.9 tok/s）**，全程 241.6 秒。
- KVMem 222,367 token 那发：全程 **631.6 秒**，折成端到端 **352 tok/s**（这里面还包含检索回填和生成的账，所以别拿它跟上面那个纯 prefill 直接对砍）。
- 单发 decode 两边同档：常规服务 15.8 tok/s，KVMem 约 17 tok/s。**长 prompt 上的慢，全在预填充和检索上，不在生成。**
- **KV 缓存复用是 KVMem 的隐藏福利**：同一份 19.2 万 token 的 prompt 再问一次，585 秒 → 224 秒（-62%）；反复问同一份长资料这种用法，它越用越划算。

资源账则有点反直觉：

![资源占用：显存反而少一点点（14,864 vs 15,774 MiB），主机内存单趟从 3.5 GB 涨到 9 GB](/images/posts/kvmem-256k-long-context/04.webp)

- **显存**：KVMem 因为 GPU 只常驻 32K 的 KV，占用反而略低（跑 25.7 万 token 那趟实测 **14,864 MiB**，常规服务是 **15,774 MiB**）。
- **主机内存**：这一趟请求把 KVMem 进程的 RSS 从 3.5 GB 一路推到 **9.0 GB**（22 GB 的机器）。这就是它的核心代价——不是显存不够，是**主机内存换上下文**。
- 还有一条纪律：块池**跨请求不释放**，连着跑八轮 20 万+ 之后主机内存被吃到约 14 GB，然后检索开始静默降级。长跑记得 `--kvmem-cpu-gb 12`。

## 九、跟压缩路线比：一个减法，一个加法

上次的压缩（billion-context 那套）和这次的分层 KV 不是竞争关系，是两道不同的手术：

| | 压缩路线 | KVMem |
|---|---|---|
| 思路 | 让输入**变小**（有损摘要） | 让窗口**变大**（KV 分层，原文直塞） |
| 20 万级输入 | 212k（17 行结论只剩 9 行保真） | 222k **原文无损耗** |
| 耗时 | 45 分钟 | 10.5 分钟 |
| 召回 | 三问全中 | 三针全中 |

**压缩省 token，KVMem 扩窗口，两个可以叠。** 真要跑超长任务，我的看法是：分层 KV 负责"别炸窗口"，压缩负责"别让上下文里塞满没用的东西"——毕竟检索回填的质量跟块结构有关，上下文越干净越稳。

## 十、我的分班表

| 场景 | 用谁 |
|---|---|
| 单发超长资料（>90k token）、反复问同一份资料 | **KVMem** |
| 多会话/多任务、需要并发 | **常规 llama-server**（开 2 槽，窗口 45k/槽） |
| 长任务 agent（不想被压缩改坏细节） | **KVMem**（关键结论还是要落盘） |

一句话总结：**16 GB 显存跑 25 万 token 上下文，成立。**代价是并发归零、主机内存要备出 9 GB 上下、预填充慢一截——但我这台机器上的长上下文活本来就是**单发批处理**，并发本来就是零。这笔账，对我是划算的。

下次想试试把 MTP 版权重也拉下来，看投机加速能不能把那个 352 tok/s 抬上去。另外 24.7 万那档的"系统性漏块"我还没吃透：到底是检索的块结构问题，还是块池的调度问题——这个得再设计一组探针，把块大小和检索 top-k 单独拿出来做变量。想做的事最优先嘛。
