2026 年 8 月，我终于在自己那台 Orange Pi 5 Max 上把本地知识库完整跑通了：文本 RAG 问答、NPU 嵌入、多模态识图，全部在本地完成，不碰任何云端。这篇文章是完整复盘——**特别是那些让我重启了七次、差点把系统搞黑的 NPU 驱动坑**。

如果你也想在 RK3588 这类开发板上跑本地大模型，希望这篇能帮你少走弯路。

## 先交代一下硬件

- **设备**：Orange Pi 5 Max，RK3588 芯片（8 核 CPU + 3 核 NPU），16GB 内存
- **系统**：官方 Debian（Bullseye），内核 6.1.43
- **模型**：Qwen3-VL-4B 量化版（文本 4.85GB + 视觉 984MB），跑在 NPU 上

![RK3588 本地知识库整体架构](/images/posts/rk3588-local-kb/01.webp)

## 总体架构：三个 systemd 服务串成链

```
rknpu098-load.service  →  rkllm.service  →  kb-service.service
(NPU 驱动 0.9.8)          (模型推理 :8080)   (知识库 :8000)
```

- **rknpu098-load**：加载外部编译的 NPU 驱动 0.9.8（这是整个部署最核心、最坑的部分）
- **rkllm**：官方推理服务，跑 Qwen3-VL-4B，提供 OpenAI 兼容 API，同时承担**文本推理**和**向量嵌入**
- **kb-service**：知识库本体（FastAPI + ChromaDB + Web UI），负责文档解析、分块、检索和问答

服务之间有依赖关系：驱动就绪 → 模型加载 → 知识库启动，全部由 systemd 保证。

## 第一个大坑：NPU 驱动的"黑屏七连"

这是全篇最惨烈的一段，值得单独写。

### 内核自带的驱动不能用

系统内核自带的 rknpu 驱动是 0.9.6，它有一个致命 bug：**无法 DMA 映射 3.75GB 以上的大模型**。4.85GB 的 Qwen3-VL 模型一加载就 `malloc 失败`，直接崩。

解决办法是屏蔽掉内置驱动，改用外部编译的 0.9.8：

```ini
# orangepiEnv.txt
extraargs=initcall_blacklist=rknpu_init
```

### 编译驱动的"官方头文件"陷阱

第一次我偷懒，用 GitHub 上的源码树编译，结果模块一加载就段错误。查了很久才发现：**驱动结构体的布局差了 8 个字节**——官方头文件编译出来偏移是 768，GitHub 源码树编出来是 776，差这 8 字节 probe 直接崩。

验证方法很硬核：

```bash
gdb -batch -ex "ptype /o struct rknpu_device" rknpu098.ko | grep multiple_domains
# 必须显示 /*  768  |     1 */  bool multiple_domains;
```

### probe 慢 = 正常现象

这个坑最离谱：驱动加载（insmod）时内核态探测要跑 **4 分钟**，systemd 默认 90 秒超时直接把它杀了，然后系统启动就卡住——**只亮蓝灯，无限期黑屏**。

排查了很久才定位：`TimeoutStartSec=300` 加上去，一切正常。probe 慢不是 bug，是这驱动就这样。

### 七次黑屏的教训

那几天我重启了七次，每一次都是蓝灯黑屏。总结出三条铁律：

1. **能用的驱动文件永远不要覆盖**——保留已知可用的 ko，新编的放一边先测
2. **一次 malloc 失败不要急着重编驱动**——我重编了一次，引入了更严重的兼容问题，白白多黑屏三次
3. **启动相关配置改动前，先看修复日志**——血泪教训

## 识图：模型"看"图片的两条路线

知识库跑通后，我想让模型直接看图。这里我踩了一个很有意思的坑，值得展开说说。

### 路线一：官方推理服务的"伪多模态"

rkllm 服务提供了 OpenAI 兼容接口，我试着用标准的 `image_url` 格式传图片路径给它，结果——**它把图片路径当成普通文本处理了**。

更迷惑的是，模型居然"回答"了，而且所有图片都返回几乎一样的内容（"一只猫在阳光下躺在沙发上"）。我一度以为多模态成功了，直到拿三张完全不同的图测试，发现输出一模一样——**这是幻觉**。模型根本没读到图片，只是被 prompt 里的 "file://..." 字符串带着编了一个看似合理的答案。

教训：**测试多模态识别，一定要拿多张内容不同的图交叉验证**。固定返回相同内容 = 模型在幻觉。

### 路线二：分离式识图流程（真正有效的）

正确的识图方式是官方 demo 的分离流程：

```
图片 → vision rknn 编码(984MB, ~20s) → 生成 img_vec
     → 释放 vision → 加载 LLM(4.85GB) → 多模态推理 → 文字描述
```

为什么分离？因为当前驱动的 IOVA 映射 **vision 模型和 LLM 不能同时驻留**（3.75GB + 984MB 共存失败），必须先编码、释放、再推理。

### 识图脚本的两个隐藏 bug

封装识图脚本时，我又踩了两个坑：

**1. demo 的交互式循环不检查 EOF**

官方 demo 是 `while(true)` 循环读 stdin 的交互程序。我用 `echo "问题" | demo` 管道喂一行，EOF 之后循环还在跑，`input_str` 变成空串，模型开始无限生成 "Hello! It seems like..."——**NPU 被占死，demo 永不退出**。

修复：问题后面必须带一行 `exit`：

```bash
printf "<image>%s\nexit\n" "$QUERY" | demo ...
```

**2. 模型服务屏蔽了所有信号**

`systemctl stop rkllm` 永远卡住：flask 推理服务在 NPU 调用期间屏蔽了 SIGTERM/SIGKILL，systemd 等满超时也杀不掉。修复方式是先后台发 stop，再直接 `kill -9` 主进程：

```bash
systemctl stop rkllm &          # 后台发停止信号
sleep 2
MPID=$(systemctl show rkllm -p MainPID --value)
kill -9 "$MPID"                 # 强杀主进程
systemctl reset-failed rkllm    # 清 failed 状态才能再次 start
```

## 批量识图：26 张图跑 30 分钟

知识库里的 Obsidian Vault 有上百张图片，不可能全走识图（每张约 1 分钟）。我筛出了 26 张**有价值的**（训练曲线、检测结果、软件截图、批注图），写了个串行脚本批量识别：

- 每张约 55~60 秒（停服务 → vision 编码 ~20s → LLM 推理 ~40s → 恢复服务）
- 识图结果存成 Markdown 描述文件，再批量入库（`images` 集合）
- 之后这些图片就能被 RAG 检索和问答了

实测识别质量不错：CrystalDiskMark 截图能认出软件名和版本，训练曲线能描述成"两条折线图"，检测结果网格图能说出是 4x4 的监控画面拼接。

## NPU 负载实测

批量识图全程采样（每 5 秒一次，543 个样本）：

- **平均负载 38.6%**，峰值 **99%**（vision 编码阶段单核打满）
- 三核频率稳定在 1GHz
- 空闲时 0%，一有推理立刻拉高——NPU 驱动工作正常

## 一些数字和感受

- 文本问答约 **5.7 tokens/s**（4B 模型在 NPU 上，够用但别指望秒回）
- 嵌入走 NPU（Qwen3-VL 的 hidden states，**10240 维**），和问答互斥（单线程），大批量入库时问答要等
- 4.85GB 模型加载后内存占用约 4.5GB（16GB 内存毫无压力）

## 最后

这次折腾最大的感受是：**开发板跑本地大模型，瓶颈永远在驱动和工程细节，而不是模型本身**。Qwen3-VL-4B 在 6 TOPS 的 NPU 上能稳定推理、能嵌入、能识图，体验完全可用——而让它跑起来的代价，是两天时间加七次黑屏。

但看到知识库能检索自己的笔记、能看懂自己拍的截图时，还是觉得值。本地模型 + 本地数据，这种"什么都自己掌控"的感觉，是云端 API 给不了的。
