# 单张 Tesla T10 16G 跑 27B 模型：Qwen3.8 Heretic-Ara + 64K 上下文实录

我一直想在自己机器上跑一个"真能干活"的本地模型，不是那种问一句答半句的玩具。手上最实在的算力是一张 Tesla T10，**显存只有 16 GB**——放在 2026 年听起来很寒酸，但挑对模型和量化，它居然能扛住 27B 参数、64K 上下文的活。

这篇就把整条链路写清楚：怎么选模型、没有 mmproj 时怎么凑出多模态、启动参数为什么这么填，以及并发 1 时它到底跑多快、吃多少资源。

## 一、选型：为什么是这个"无审查"的 Heretic-Ara

我用的权重是 **Qwen3.8-27B-Heretic-Ara-16GB-VRAM-IQ4-XS-MTP-GGUF**。这个模型是基于 **Heretic Arbitrary-Rank Ablation** 做的无审查版本——直白说就是在原模型上做了一层定向的"阉割疗法"，把拒答和对齐冗余留在门外，同时**性能更好、体积更小**。

对我这种单卡用户，它的关键好处是"16GB VRAM"版本这个定位本身就说明了好处：IQ4_XS 量化把权重压到 13 GB 出头，正好塞进 16 GB 显存里跑。

仓库里其实有 **MTP** 和**非 MTP**两套权重。MTP（多 token 预测）听着很美，但我这次用的是 **3.0 的非 MTP 版本**——理由很朴素：我要的是"稳定地一直能跑"，而不是"峰值再快一点但偶尔抽风"。MTP 那套留着以后有空再折腾。

## 二、坑：这个模型没有 mmproj

装完发现一个现实问题：**它不带 mmproj 文件**，也就是纯文本能用，图片喂不进去。

要图像能力，就得自己去找同系列 Qwen3.8-27B 的投影层来拼。我用的是 **dealignai/Qwen3.8-27B-UNCENSORED-GGUF** 里的 mmproj（f16 版本），跟着主权重一起加载。实测图文混着喂是通的——图片能正常被"看见"并描述。

这里有个经验：跨仓库拼权重和投影层是可行的，但**版本要对上**（同一个 base 模型的 hidden size、视觉塔结构得一致），否则要么加载报错，要么模型"看得到但看不懂"，输出一些像在瞎猜的描述。

## 三、怎么起的：llama.cpp 参数逐条说

服务是 llama.cpp 的 `llama-server`，挂在 systemd 单元里开机自启，日志走 journal，对外提供 OpenAI 兼容接口。核心参数如下，每条都有它的理由：

- `-ngl 99`：全部层丢给 GPU。都上卡了，别留一半在 CPU 上拖后腿。
- `-c 65536`：**64K 上下文**。这是这张卡的甜点位——再往上显存就不够了。
- `-ctk q8_0 -ctv q8_0`：**KV cache 做 Q8 量化**。这是能把 64K 塞进 16 GB 的关键：不量化的话光 KV 就把显存吃穿了。
- `-b 1024 -ub 512`：批处理和 micro-batch 大小，配合显存和吞吐调出来的折中。
- `-t 4`：CPU 线程数，留给 tokenize 等零碎工作。
- `-fa on`：开启 FlashAttention，长上下文省显存、提速度。
- `--jinja`：走模型自带的 chat template，工具调用、思考链这些格式才对得上。
- `--mmproj <文件> --no-mmproj-offload`：加载投影层，但视觉塔**不**放显存（显存太紧了，留主模型用）。
- 单槽（不开并发）：一张卡、一份 KV cache，开并发只会互相抢。

模型加载后，任何 OpenAI 兼容的客户端都能直接接上——我平时就是让本地的编码 agent、脚本都指向它。

## 四、实测吞吐：并发 1

测法是逐级灌长提示词（1k → 64.5k），每次都让 KV cache 冷启动，并发固定 1。数据如下：

| 提示词长度 (tokens) | TTFT (ms) | ITL平均 (ms) | 预填充 (tokens/s) | 输出 (tokens/s) |
|---:|---:|---:|---:|---:|
| 993 | 2114 | 51.61 | 499.14 | 19.38 |
| 2030 | 3914 | 52.12 | **537.10** | 19.19 |
| 3982 | 7629 | 54.49 | 533.67 | 18.35 |
| 8008 | 15402 | 54.13 | 529.74 | 18.47 |
| 15999 | 31872 | 56.96 | 506.76 | 17.56 |
| 32042 | 69886 | 62.89 | 462.48 | 15.90 |
| 64555 | 164851 | 76.76 | 393.94 | 13.03 |

![单卡 T10 并发 1 下预填充与输出吞吐随提示词长度的变化](/images/posts/local-llm-t10-qwen38-heretic-ara/01.webp)

一句话总结这组数：**预填充 ~400–540 tok/s、输出 ~13–19 tok/s（平均 17.4）**。预填充在 2k 左右达到峰值 537，随后随长度缓降，到 64K 掉到 394（-27%）；输出从 19.4 降到 13.0，单 token 间隔从 51.6 ms 拉长到 76.8 ms。

更值得注意的其实是 **TTFT**：64.5k 的提示词要 **165 秒**才吐第一个字。这意味着长上下文只适合批处理、离线任务，别指望拿它做长对话式的交互。

## 五、资源占用：瓶颈全在显卡上

压测期间我每秒采一次样，把 GPU 核心、显存、系统内存、CPU、磁盘 IO 全部记下来：

![资源占用时间线：8k → 32k → 64.5k 提示词](/images/posts/local-llm-t10-qwen38-heretic-ara/03.webp)

- **显卡核心**：峰值 **100%**，长上下文阶段基本贴着满跑；显存控制器利用率峰值 93%。
- **显存**：峰值 **15740 / 15946 MiB（≈98.7%）**，最低只剩 **200 MiB 出头**——权重 13 GB + Q8 的 64K KV cache，几乎把卡榨干。
- **功耗/温度**：峰值 **159.5 W**（上限 150 W，长上下文会短时顶到限额之上），温度 61 °C。
- **CPU**：4 vCPU 合计峰值只有 **37%**，全程没有一秒超过 90%——CPU 完全不是瓶颈。
- **内存**：峰值 11.5 GB / 23.5 GB。其中 llama-server 的驻留集 10.9 GB，因为权重是 mmap 进来的，page cache 也算在里面。
- **磁盘 IO**：读峰值 1.2 MB/s、写峰值 4.2 MB/s，PSI IO 全程 0.00。推理期几乎不碰盘——权重常驻显存，那点写是日志落盘。

所以结论很干净：**这是个纯 GPU 瓶颈的活**。CPU、内存、磁盘全是闲着的，想提性能只能从显存上做文章。

而显存已经没有余地了。这意味着三件事都别想了：把上下文开过 64K（模型本身训练上限有 262144，是硬件拖后腿）、加并发槽位、或者换更高精度的量化。要动就得先把 KV 从 Q8 降到 Q4，用精度换空间。

## 六、它现在在干什么

这套配置我主要拿来干三件事：

1. **本地 AI agent**：接上编码 agent 当后端，不联网、不怕数据出门，响应速度也够用。
2. **图像反推**：借来的 mmproj 让它能看图描述，反推出来的描述再拿去二次创作或者整理素材库。
3. **提示词优化**：把粗糙的一句话丢给它，让它补细节、补约束、补风格，比自己憋词快得多。

对一个 16 GB 显存的单卡环境来说，**27B 参数、4bit 量化、64K 上下文的组合用来做这三件事已经足够**。瓶颈当然有——长上下文的首字延迟摆在那里——但它是我自己的机器、自己的模型，不担心限额、不担心内容被审查，这一点比几个 tok/s 的差距重要得多。
